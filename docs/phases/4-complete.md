# Phase 4 — Complete

**Exit criteria:** every optimization pass has a snapshot test, and the full end-to-end
suite produces identical output at `-O0`, `-O1` and `-O2`.

**Status:** met. `./check` passes in 3s at 196 MiB, against budgets of 300s and 3072 MiB.
22 packages report `ok`; 25,514 lines of implementation including tests.

## What was built

**`internal/ir`** — the SSA intermediate representation (ADR-0016): a control-flow graph
of basic blocks, built *from bytecode* rather than from the AST, so that `-O0`, `-O1` and
`-O2` share one lowering and differ only by which passes ran. φ insertion is on-demand
(Braun, Buchwald, Hack, Leißa, Mallon, Zwinkau, CC 2013): a block reads a variable it does
not locally define, gets an incomplete φ if its predecessors are not all known yet, and
the φ is completed when the block is sealed. Dominators come from the iterative algorithm
of Cooper, Harvey and Kennedy; natural loops fall out of back edges (an edge whose target
dominates its source), and a loop gets a preheader when it has exactly one entry from
outside — the one condition that makes hoisting into it sound.

**`internal/opt`** — constant folding, copy propagation, common-subexpression
elimination, loop-invariant code motion, escape analysis, dead-code elimination,
unreachable-block removal, and inlining with a fixed instruction-count budget. Three of
them are shaped by ADR-0005 rather than by convention, because trapping is the language's
one place where "optimized" and "unobservable" could pull apart:

- Folding an operation that would trap replaces it with the trap itself, in the same
  place, never with a wrapped constant and never by deleting it.
- Dead-code elimination keeps an unused operation that can trap on its operands — an
  ignored `a + b` that would overflow must still stop the program.
- Loop-invariant code motion never hoists a trapping operation: a loop that never
  executes must not start trapping just because the optimizer ran.

Common-subexpression elimination never merges two allocations, because `ref_eq` can tell
them apart (spec/04-expressions.md) — object identity is observable, so two `Point { x: 1
}` literals stay two objects no matter how equal their fields are.

**`internal/mono`** — monomorphization (ADR-0010) of *call dispatch*. Every non-generic
function is a root with exactly one instance, exactly as before this package existed.
A generic function is compiled once per distinct tuple of type arguments a call site
actually needs, discovered by a breadth-first walk from the roots: `max2[i64]` and
`max2[Money]` are two different bytecode functions with two different bodies, because
`a.cmp(b)` inside `max2[T: Ord]` resolves to a different callee in each — the VM's
builtin comparison in one, `Money`'s own `cmp` method in the other — and only the
concrete instantiation knows which. Polymorphic recursion (a generic function that calls
itself at a strictly larger type, producing an infinite instantiation set) is rejected as
`E0055` once the chain exceeds a depth of 64, with the chain in the diagnostic.

Rejecting `E0055` is a legality question, so `mono.Program` runs during checking
(gated in `internal/driver` exactly like `check.Program`, on the same bag) rather than
during code generation — `originc check` and `originc run` must reach the same verdict.

**Tests:** unit tests for SSA construction, dominators, every optimizer pass and every
monomorphization behavior (repeated calls at one type sharing an instance, a
compiler-provided impl leaving a call unresolved for the builtin fallback, deterministic
instance ordering across 50 runs); a per-pass IR snapshot with declared prerequisites, so
a case exercises the pass instead of producing an empty diff; effect tests asserting
inlining, escape analysis, folding and loop hoisting actually fire in generated bytecode,
not just that output is unchanged; a pass-free IR round trip so a divergence has one
suspect; and an end-to-end case with a user-defined trait impl called generically, which
fails without `internal/mono` and passes with it.

## The decision that shaped this phase

Phase 3's doc predicted that monomorphization would retire the tagged-slot heap
representation, giving every instantiation an exact object layout. That turned out to be
two separable pieces of work wearing one name. **Call dispatch** — which concrete
function a generic call site reaches — has to be right for the language to be correct at
all, and Phase 4 delivers it: without it, a trait method called on a type parameter has
no way to reach a user-written impl, which is a soundness bug, not a missing
optimization. **Object layout** — giving `Point[T]` a different, exact word layout per
`T` instead of a tagged slot per field — is a performance and code-size question that
needs the backend's cooperation (`internal/layout` is the GC's and, from Phase 5, the
backend's shared contract per `CLAUDE.md`), and doing it before there is a backend to
share it with would mean guessing at the interface twice. `docs/deferred.md` now reflects
that split rather than the earlier prediction.

## What surprised me

1. **The bug was real, not hypothetical.** Before `internal/mono` existed, a program with
   a user-defined `impl Ord for Money` called generically through `max2[T: Ord]` compiled
   and ran — and printed the wrong answer, silently, on the VM. The checker resolves a
   trait method on a concrete type statically (no vtable, per ADR-0010), but a method
   called on a type *parameter* inside a generic body has nothing concrete to resolve
   against until the parameter is substituted, and nothing before this phase substituted
   it. Writing the failing case first — building a small program that used a
   compiler-provided impl (which happened to work by accident, because the VM's builtin
   dispatch already switched correctly on runtime type tags) alongside a user-defined one
   (which did not) — is what separated the coincidence from the fix.

2. **Sealing a block in map order made every IR snapshot flaky.** Completing a pending φ
   reads its variable in every predecessor, which can create further pending φs; Go
   iterates a map in randomized order, so which φ got created first — and therefore its
   value number — changed from run to run. Nothing about this was wrong *semantically*:
   every build was a correct SSA form, just a differently numbered one. It only became
   visible because the snapshot tests compare printed IR textually. The fix sorts the
   pending set by local-slot number before completing it, which is arbitrary but stable —
   the property that was missing was never "this order," only "some fixed order."

3. **Writing a case that exercises `copy-propagate` alone needed two prerequisite
   passes, not the one I expected.** A φ with two distinct operands only becomes trivial
   once folding resolves the branch *and* the now-dead arm is actually removed —
   `unreachable-blocks` has to run first, or the φ still has an unreachable predecessor
   feeding it a value nobody can reach. `Pass.Needs` exists so a per-pass snapshot states
   its prerequisites instead of silently depending on pipeline order elsewhere.
